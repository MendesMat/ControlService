# Record and API contract

## Purpose

Decide correctly, in any feature, how a record is shaped, saved, versioned, listed and how a failure is answered. The front-end already depends on this contract.

## Source of truth

This skill is an index of decision rules, not a copy of the rules. The canonical text is:

- `docs/product/conventions.md` (CNV-01 to CNV-20)
- `docs/api/conventions.md` (API-01 to API-15, and the error code table)

Paths are from the repository root. Before asserting a message, a field name or a status in code or in a test, open the cited rule and copy from there (CNV-16). If this skill and `docs/` disagree, `docs/` wins: stop and tell the owner. A pull request that changes a CNV or API rule updates this file too.

## When to use

- Adding a field to a request, a response or an aggregate.
- Adding or changing an endpoint, a list, or an error code.
- Writing a validation or confirmation message.
- Implementing create, update, deactivate, reactivate or delete of any record.

Feature rules live in `domain-users`, `domain-authentication` and `domain-permissions`; they assume this skill.

## Core concepts

| Concept | Meaning | In code |
|---|---|---|
| Record ("cadastro") | An aggregate with id, audit fields and version | `AuditedAggregate` |
| Version ("versão") | Opaque value that changes on every change | `Version` (`xmin`), `version`, `ETag`, `If-Match` |
| Authorship ("autoria") | Who created and who last changed, and when | `createdAt`, `createdBy`, `updatedAt`, `updatedBy` |
| Informational document | CPF, phone, CEP: lookup and display only | `Cpf`, `PhoneNumber`, `Cep` |
| System record | Admin user and Gerenciador profile; fixed ids, cannot change | `IsSystem`, `SystemIds` |

## Decision rules

### Shaping a field

- Name it in English camelCase, the same in code, storage and JSON (CNV-02).
- An optional text left blank is `""`. Never `null`, never omitted. Trim all stored text (CNV-03).
- Plain dates are `YYYY-MM-DD`; timestamps are full UTC date-time (CNV-05).
- The `id` is a UUID v7 generated by the server. Never accept an id from the client on creation (CNV-04).

### CPF, phone and CEP

- Accept them with or without a mask; store and return digits only (CNV-07, API-02).
- Never make another rule depend on them, and never make them unique (CNV-06).
- Search by CPF compares digits only (CNV-08).

### Uniqueness

- A unique name is compared ignoring case, accents and outer spaces, and guaranteed by a unique index on the normalized copy (CNV-09). In code: `TextNormalization.Normalize`.
- The server performs every uniqueness check (API-09).
- A duplicate is a **400 `validation_failed` under the field**, never a 409 (API-13).

### Audit fields

- The client never sends them and can never edit them (CNV-10).
- On creation, `updatedAt` and `updatedBy` equal `createdAt` and `createdBy` (CNV-19).
- Records the system creates by itself are authored by the Admin (CNV-20).
- Handlers never set them: `AuditFieldsInterceptor` does (`docs/agents/guides/architecture.md`, Persistence).
- Single-record responses add the display names `createdByName` and `updatedByName` (API-03).

### Saving over someone else's change

- Every read returns `version` in the body and in `ETag` (API-06).
- Change, deactivate, reactivate and delete require the version in `If-Match` (CNV-12).
- If the version changed: refuse, write nothing, answer 409 `concurrency_conflict` with `details.updatedByName` (CNV-13).
- Treat the version as opaque. Never parse it, compare it by order, or compute it.

### Routes and responses

- Every route starts with `/api/v1` (API-01).
- Personal data and tokens travel in the body, never in the URL, even for a read-like operation (API-04).
- Creation answers `201 Created`, the created record and a `Location` header (API-05).
- Lists are paged, searched, sorted and counted on the server: `{ items, page, pageSize, totalCount }` (API-07). Only small reference lists come whole (API-08).
- Every endpoint declares its screen and minimum level (API-11). The levels are owned by `domain-permissions`.

### Failures

- An expected failure is a `Result` error translated to Problem Details with `code`, `message`, `errors`, `details`, `traceId` (API-12).
- `validation_failed` has a fixed top message (API-15); each field message is under `errors`, keyed by the camelCase model path (`address.cep`, `emergencyContact.phone`).
- An unexpected failure answers 500 `unexpected_error` with the generic message; the cause goes only to logs (API-14).
- The complete code table is `docs/api/conventions.md#error-codes`. Its code counterpart is `ErrorStatusCodes`; an unmapped code throws and becomes the 500.

### Messages

- Plain Portuguese, no technical terms (CNV-15), copied verbatim from the feature document (CNV-16).
- A message that does not exist in the feature document is a gap: ask the owner, then add it there with a new rule ID in the same pull request.
- Confirmations name the person's record or access, not the person (CNV-17).

## Invariants

1. The back-end enforces every rule. A hidden button is never the protection (CNV-01).
2. No write happens on a version mismatch (CNV-13).
3. Audit fields and ids come only from the server (CNV-04, CNV-10).
4. Rule IDs are never reused or renumbered (`docs/README.md#rule-ids`).

## Forbidden

- Returning `null` or omitting an optional text field.
- Storing or returning a masked CPF, phone or CEP.
- Answering a duplicate name or login with 409.
- Putting a full name, CPF, login suggestion input or link token in a route or query string.
- Writing a message from memory, or translating one.
- Adding an error code, route or response field without the owner's approval (`AGENTS.md`, "Ask the owner first").

## Exceptions

- Passwords are never trimmed (AUTH-16, owned by `domain-authentication`).
- `account_inactive` has two statuses and `locked_out` has two causes (owned by `domain-authentication`).
- Listing permission profiles is not paged (API-08).
- CNV-11, CNV-14 and CNV-18 describe what the front-end shows (footer, conflict dialog, error summary). The back-end only supplies the data they need.

## Terminology

| Term | Means | Do not confuse with |
|---|---|---|
| `version` | Opaque concurrency token | The API version in `/api/v1` |
| "Cadastro" | A record | The act of signing up (nobody signs up: AUTH-01) |
| `validation_failed` | Any field error, including duplicates | `concurrency_conflict` and the other 409 business refusals |
| `details` | Extra data of an error (`updatedByName`, `userNames`) | `errors`, the per-field messages |

## Open questions (not rules)

Full change history (OQ-02) and live list refresh (OQ-03) are undecided: `docs/product/open-questions.md`. Ask before building anything that depends on them.

## How to verify

- A new error code has a row in `ErrorStatusCodes` and a case in `ErrorResultsTests`.
- An API integration test asserts the status, the `code` and the verbatim message, and for updates the 409 path with a stale `If-Match`.
- A unique rule has an integration test that hits the unique index.
