# API conventions

What every endpoint of the back-end has in common: addresses, paging, versions, errors and the session mechanism the front-end relies on. The operations of each feature are in its document in [product/features](../product/features/).

The front-end calls the API only through its `api` object. Replacing the prototype's simulated server with an HTTP client that offers the same methods, responses and errors must require no change to the screens ([front-end prototype](../frontend/simulated-server.md)).

## Addresses and format

| ID | Rule |
|---|---|
| API-01 | Every route starts with `/api/v1` (ADR-0003). A breaking change goes to `/api/v2`. |
| API-02 | Request and response bodies are JSON with the field names of the data model (CNV-02). CPF, phone and CEP are accepted with or without a mask and returned digits only (CNV-07). |
| API-03 | Single-record responses include the display names of who acted: `createdByName`, `updatedByName` and, for users, `deactivatedByName`. |
| API-04 | Personal data and tokens never travel in the URL, only in the body (for example `suggestLogin` and the authentication links), so they are not written to logs. |

## Creating and versioning

| ID | Rule |
|---|---|
| API-05 | Creation returns `201 Created` with the created record, including the `id` generated by the server, and a `Location` header. |
| API-06 | Reading a record returns its `version` in the body and in the `ETag` header. Changing, deactivating, reactivating and deleting send it back in the `If-Match` header (ADR-0014, CNV-12). |

## Lists

| ID | Rule |
|---|---|
| API-07 | Lists are **paged on the server**: the client asks only for what it shows ("page 1 of users with 'silva', 10 per page"), and the server searches, sorts, counts and returns `{ items, page, pageSize, totalCount }` (ADR-0017). This keeps large screens fast and never sends the browser data the person may not see. |
| API-08 | Small reference lists come whole: permission profiles, the screen catalog and, in the future, payment methods. |
| API-09 | Every uniqueness check (login, display name, profile name) is done by the server. |

## Authentication and authorization

| ID | Rule |
|---|---|
| API-10 | Authenticated requests send the access token as `Authorization: Bearer <token>`. The refresh token travels only in its `HttpOnly` cookie, so requests must be sent with credentials (`credentials: 'include'`) from `localhost` or the API's own site (AUTH-17). |
| API-11 | Every endpoint declares the screen and minimum level it requires (PERM-03). Requests above the person's level get 403 `forbidden`. |

## Errors

| ID | Rule |
|---|---|
| API-12 | Expected failures return Problem Details (RFC 9457) with the extensions `code`, `message` (Portuguese, ready to show), `errors` and `details` when applicable, and `traceId` (ADR-0009). Unexpected failures return 500 with a generic Portuguese message; details go only to the logs. |
| API-13 | Duplicated login, display name or profile name are validation errors (400 `validation_failed`) with the message under the field, like any other validation. |

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "Bad Request",
  "status": 400,
  "code": "validation_failed",
  "message": "Alguns campos precisam ser corrigidos.",
  "errors": {
    "login": ["Já existe um usuário com o login “ana.souza”. Escolha outro."],
    "address.cep": ["O CEP precisa ter 8 números."]
  },
  "traceId": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01"
}
```

`errors` uses the camelCase model path of each field (`login`, `address.cep`, `emergencyContact.phone`); on the password screens the fields are `password` and `passwordConfirmation`. The front-end's HTTP client converts the response into its `ApiError`:

| Back-end response | `ApiError` |
|---|---|
| `status`, `code`, `message` | `status`, `code`, `message` |
| `errors` (first message of each field) | `details.fields` |
| `details` (e.g. `updatedByName`, `userNames`) | `details` |

### Error codes

| Status | `code` | Situation | What the front-end does |
|---|---|---|---|
| 400 | `validation_failed` | Invalid fields | Shows each message under its field and, on forms, a notice at the top with how many fields need fixing (CNV-18) |
| 401 | `invalid_credentials` | Wrong login or password | Shows the message on the sign-in screen |
| 401 | `session_expired` | The session ended | Shows the sign-in screen over the system, keeping the tabs |
| 401 | `account_inactive` | The account was deactivated **during a session** | Shows the sign-in screen with the message |
| 401 | `password_change_required` | The initial password was not changed yet | Shows the change-password screen |
| 403 | `account_inactive` | **At sign-in**: correct password, deactivated account | Shows the message on the sign-in screen |
| 403 | `forbidden` | Operation above the person's level | Refreshes the menu and shows the no-access message |
| 404 | `not_found` | Record does not exist | Shows "Registro não encontrado" |
| 409 | `concurrency_conflict` | Someone else changed the record; `details.updatedByName` says who | Asks whether to reload or stay on the screen (CNV-14) |
| 409 | `profile_in_use` | Profile assigned to users; `details.userNames` says who | Explains who uses the profile |
| 409 | `system_record`, `self_deactivation`, `not_pending`, `not_inactive`, `email_missing` | Business rule refused | Shows the message in a notice |
| 410 | `link_invalid` | Link expired or already used | Shows the invalid-link screen |
| 429 | `locked_out` | Lockout or rate limit, with `Retry-After` | Shows the wait message |

Any other failure shows a generic message and keeps what the person typed.

## OpenAPI

The OpenAPI document is generated from the endpoints and browsable at `/scalar` in development (ADR-0004). Endpoint summaries and descriptions are in English; examples of user-facing messages stay in Portuguese.
