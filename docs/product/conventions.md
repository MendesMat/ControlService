# Product conventions

Rules that apply to every record and every screen. Feature documents in [features/](features/) only describe what is specific to them; read this file together with any of them.

Rule IDs (`CNV-nn`) are stable: cite them in tests, pull requests and conversations. See [how rule IDs work](../README.md#rule-ids).

## Enforcement

| ID | Rule |
|---|---|
| CNV-01 | The back-end enforces every rule in these documents. The browser is never the only barrier: hiding a button is a convenience, not a protection. |

## Record fields

| ID | Rule |
|---|---|
| CNV-02 | Field names are English camelCase, exactly as in code and in stored data (`fullName`, `profileIds`, `levels`). |
| CNV-03 | Optional fields left blank are an empty string (`""`), never `null` and never omitted. All text is stored without leading or trailing spaces. |
| CNV-04 | Every record has an `id`: a GUID (UUID v7) **generated by the server** on creation. Clients never send it; it comes back in the creation response (ADR-0012). System records use fixed, well-known GUIDs. |
| CNV-05 | Dates use ISO 8601: `YYYY-MM-DD` for plain dates (birth date) and full UTC date-time for timestamps (`updatedAt`). |

## Informational documents: CPF, phone and CEP

| ID | Rule |
|---|---|
| CNV-06 | CPF, phone and CEP are **informational**: they are used for lookup and display, and no other rule depends on them. |
| CNV-07 | They are stored **digits only**. The server accepts them with or without a mask and removes the formatting before storing. The mask is applied only for display, and the field formats itself while the person types. |
| CNV-08 | Searching by CPF compares digits only: any way of typing the number finds the person. |

| Field | Stored | Displayed |
|---|---|---|
| CPF | `52998224725` | `529.982.247-25` |
| CEP | `20040020` | `20040-020` |
| Phone, 11 digits | `21987654321` | `(21) 98765-4321` |
| Phone, 10 digits | `2134567890` | `(21) 3456-7890` |

## Name uniqueness

| ID | Rule |
|---|---|
| CNV-09 | When a name must be unique (user display name, profile name), the comparison ignores upper and lower case, accents and leading or trailing spaces: "Ana Souza", "ana souza" and "Ána Souza" are the same name. The database guarantees it with a unique index on a normalized copy (ADR-0011). |

## Authorship (audit)

| ID | Rule |
|---|---|
| CNV-10 | Every record stores who created it and who last changed it, and when. The server fills these fields; they can never be edited by the client (ADR-0015). |
| CNV-11 | Every open record shows a footer with the display name of who acted, in Brasília time. New records that were never saved show no footer. |

| Field | Content |
|---|---|
| `createdAt` | Creation date and time, ISO 8601 UTC |
| `createdBy` | `id` of the user who created the record |
| `updatedAt` | Last change date and time, ISO 8601 UTC |
| `updatedBy` | `id` of the user who made the last change |

Footer example, side by side (stacked on narrow screens):

> Criado por Admin em 12/09/2026 às 09:58
> Última alteração por Bruno Lima em 20/09/2026 às 14:41

A full field-by-field history is not part of this stage (see [open questions](open-questions.md)).

## Several people editing at the same time (optimistic concurrency)

| ID | Rule |
|---|---|
| CNV-12 | Every record has a `version`, an opaque value that changes on every change. Whoever reads a record receives it and must send it back when saving, deactivating, reactivating or deleting (ADR-0014). |
| CNV-13 | If the version changed in the meantime, the operation is **refused**: nothing is written, and what the person typed stays on screen. |
| CNV-14 | The person chooses between **"Recarregar"** (discard their changes and show the current version) and **"Continuar aqui"** (keep the screen as it is, to copy what they need before reloading). |

The dialog title is **Outra pessoa alterou este cadastro**, and the message is:

> Este cadastro foi alterado por *{nome de exibição}* enquanto você editava. Recarregue para ver a versão atual.

**Example.** Ana and Bruno open Carlos's record. Ana fixes the phone and saves. When Bruno tries to save his fix to the RG, the system refuses and says Ana changed the record. Without this rule, Bruno's save would silently undo Ana's fix. The same rule protects someone who opens the same record in two tabs.

## User-facing messages

| ID | Rule |
|---|---|
| CNV-15 | Every text shown to people is in plain Portuguese, without technical terms, for people who are not familiar with technology. The messages in these documents are the reference for the tone of any new message. |
| CNV-16 | Messages are written **exactly** as they must appear: code copies them verbatim. A new message is added to the feature document in the same pull request. |
| CNV-17 | Confirmation messages refer to the person's record or access, not to the person ("Cadastro de Ana Souza criado"), so the grammar is correct for any name. |
| CNV-18 | When a form has errors, the screen shows at the top how many fields need fixing and takes the person to the first one. Each message appears below its field and disappears as soon as the field is fixed. |

Messages that mention an e-mail include, in the prototype, the button **Ver e-mail**, which opens the test inbox.
