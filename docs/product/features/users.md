# Users

Registering people, keeping their data, deactivating and reactivating them. Signing in and passwords are in [authentication](authentication.md); what a user can access comes from [permission profiles](permission-profiles.md).

- **Screen:** Usuários, key `gerenciamento/usuarios`. The record form has the sections Dados pessoais, Acesso ao sistema, Telefone e endereço, Contato de emergência, Assinatura and Perfis de permissão.
- **Decisions:** in the [decisions document](../../decisoes-de-arquitetura.md): 3 (value objects), 12 (ids), 15 (deactivation), 16 (Admin), 17 (paging), 21 (temporary password).
- **Read with:** [conventions](../conventions.md), [API conventions](../../api/conventions.md), [glossary](../glossary.md).

**Not built yet.** These rules are the decided behavior. The code still has the `pending` status, the `activatedAt` field and a required e-mail, left over from the plan with activation links; they change with the users endpoints (issue #11).

## Data model

Collection `users`. Besides the fields below, every user has the audit fields and `version` ([conventions](../conventions.md#authorship-audit)).

### Access

| Field | Type | Required | Format and notes |
|---|---|---|---|
| `id` | text | yes | GUID generated by the server (CNV-04) |
| `login` | text | yes | Name used to sign in, e.g. `ana.souza`. See USR-05 and USR-06 |
| `email` | text | no | Contact information only: no rule of the system depends on it while access by e-mail is postponed. **Not unique**: two people may share a department mailbox |
| `status` | text | yes | `active` or `inactive`. Controlled by the system, never edited directly |
| `deactivatedAt` | text | no | Deactivation date and time. `""` if not deactivated |
| `deactivatedBy` | text | no | `id` of who deactivated. `""` if not deactivated |

Passwords and the lockout counter are not part of the record (AUTH-19). Whether the person still has a temporary password belongs to the credential, not to the record.

### Personal data

| Field | Type | Required | Format and notes |
|---|---|---|---|
| `fullName` | text | yes | Full name |
| `displayName` | text | yes | Short name that identifies the person in the system and in activity records, e.g. "Ana Souza". Unique (USR-03) |
| `cpf` | text | no | 11 digits, no dots or dash: `52998224725`. See USR-08 |
| `rg` | text | no | Free text, no format and no validation |
| `birthDate` | text | no | `YYYY-MM-DD`, not in the future |
| `bloodType` | text | no | One of `A+`, `A-`, `B+`, `B-`, `AB+`, `AB-`, `O+`, `O-`, or `""` |
| `phone` | text | no | 10 digits (landline) or 11 (mobile), with area code, no formatting: `21987654321` |
| `address` | object | yes | Always present, even with every field empty |
| `emergencyContact` | object | yes | Always present, even with every field empty |
| `signature` | text | no | Signature image (see [signature](#signature)) |
| `profileIds` | list of text | yes | Ids of the person's permission profiles. May be empty (USR-13, USR-21) |

`address` (all optional): `cep` (8 digits, `20040020`), `street`, `number` (text, to accept "S/N" or "120A"), `complement` (e.g. "apto 101"), `district`, `city`. The state (UF) is not part of the record.

`emergencyContact` (all optional): `name`, `relationship` (free text, e.g. "mãe", "irmão"), `phone` (same format as the user's `phone`).

CPF, phone, address, emergency contact and blood type are personal data under the LGPD, and blood type is sensitive (health) data: never log them, and use only fictitious values in tests and examples.

## Validation on save

Messages are verbatim, in Portuguese (CNV-16). The error path of each field is the one in the table.

| ID | Field | Rule | Message |
|---|---|---|---|
| USR-01 | `fullName` | Required. | Informe o nome completo. |
| USR-02 | `displayName` | Required. | Informe como o nome vai aparecer no sistema. |
| USR-03 | `displayName` | Unique among **all** users, including the Admin and deactivated users, with the normalized comparison of CNV-09. It identifies each person without ambiguity in activity records. | Já existe um usuário chamado “*{nome existente}*”. Use um nome diferente, por exemplo acrescentando o sobrenome ou o setor. |
| USR-04 | `login` | Required. | Informe o login. |
| USR-05 | `login` | 3 to 30 characters: unaccented letters, digits, dot, hyphen and underscore. Stored in lowercase. | O login deve ter de 3 a 30 caracteres, usando só letras sem acento, números, ponto, hífen ou sublinhado. |
| USR-06 | `login` | Unique among **all** users, including the Admin and deactivated users, ignoring case. | Já existe um usuário com o login “*{login}*”. Escolha outro. |
| USR-07 | `email` | Optional. When filled in, it must be in a valid e-mail format. **Not unique.** | Este e-mail não parece válido. Confira se ele tem @ e o domínio, por exemplo ana@empresa.com.br. |
| USR-08 | `cpf` | Optional. When filled in, it must pass the [check digits](#cpf-check-digits); CPFs with all digits equal, such as `111.111.111-11`, are refused. **Not unique.** | Este CPF não é válido. Confira os números ou deixe o campo em branco. |
| USR-09 | `birthDate` | When filled in, it cannot be after today. | A data de nascimento não pode ser no futuro. |
| USR-10 | `phone` | When filled in, 10 or 11 digits. | Digite o telefone com DDD. Ex.: (21) 98765-4321. |
| USR-11 | `address.cep` | When filled in, 8 digits. | O CEP precisa ter 8 números. |
| USR-12 | `emergencyContact.phone` | Same rule as USR-10. | Digite o telefone com DDD. Ex.: (21) 98765-4321. |
| USR-13 | `profileIds` | May be empty. Ids of profiles that do not exist are discarded on save. | — |
| USR-35 | `temporaryPassword` | Only when registering a new user: required, with the minimum length of AUTH-16. It is never returned and is not part of the record (AUTH-19). | Missing: Informe a senha temporária. — Too short: A senha precisa ter pelo menos 8 caracteres. |
| USR-26 | `bloodType` | When filled in, must be one of the closed list `A+`, `A-`, `B+`, `B-`, `AB+`, `AB-`, `O+`, `O-`. | Este tipo sanguíneo não é válido. |

Duplicates (USR-03, USR-06) are validation errors like the others, shown under the field (decision 7).

### CPF check digits

For the first check digit, multiply the first 9 digits by the weights 10, 9, 8, …, 2 and add them up. Multiply the result by 10 and divide by 11; the remainder is the digit, and a remainder of 10 means 0. For the second, repeat with the first 10 digits and the weights 11, 10, …, 2.

## Login suggestion

| ID | Rule |
|---|---|
| USR-14 | When registering a user, the system suggests a login from the full name: first and last names, without accents, lowercase, separated by a dot. "Ana Paula Souza" gives `ana.souza`. If it is taken, a number is appended: `ana.souza2`, `ana.souza3`. The person may accept it or type another login. |
| USR-15 | Special cases: a one-word name gives that word ("Madalena" → `madalena`); characters outside the login rule (apostrophes, extra spaces, symbols) are removed ("Joana D'Ávila" → `joana.davila`); a long result is cut to fit 30 characters **including** the appended number; a result shorter than 3 characters gives no suggestion ("Li"). |
| USR-31 | Name suffixes ("Filho", "Júnior", "Neto") are taken literally, as part of the last name: "João Souza Filho" gives `joao.filho`. When cutting a long result to fit 30 characters (USR-15) leaves a trailing `.`, `-` or `_`, that character is also removed. |

In a new record, the login is suggested while the full name is typed, until someone types a login of their own. The save button of a new record is **Cadastrar usuário**.

## Deactivation and reactivation

| ID | Rule |
|---|---|
| USR-16 | Users are **never deleted**, only deactivated: authorship and activity records point to users, and deleting one would leave them without an owner (decision 15). |
| USR-17 | Deactivating a user: status becomes `inactive`, with date and author of the deactivation; the person is signed out on their next action and cannot sign in again (AUTH-18, AUTH-09); their sessions end (AUTH-21); the login and display name stay reserved; the name keeps appearing in history and authorship. |
| USR-18 | A deactivated user can be reactivated with **Reativar usuário**, without a confirmation. They become `active` again with the password they had; if it was still a temporary one, the mandatory change is still required (AUTH-14). |
| USR-29 | Reactivating a user who is not `inactive` is refused with the message *"Só é possível reativar um acesso desativado."* |
| USR-19 | Nobody can deactivate themselves, so nobody loses access by mistake. The Admin can never be deactivated. |
| USR-27 | Trying to deactivate one's own account is refused with the message *"Você não pode desativar o seu próprio acesso."* |
| USR-20 | The list's **Situação** filter starts at "Ativos", hiding deactivated users. The other options are "Só desativados" and "Todos". |
| USR-30 | Deactivating a user who is already deactivated changes nothing: the status stays `inactive`, and the date and author of the **first** deactivation are kept. |

The deactivation confirmation is: *{Nome} não vai mais conseguir entrar no sistema. Você pode reativar depois.* If the record has unsaved changes, it adds: *As alterações não salvas neste cadastro serão descartadas.* After deactivating or reactivating, the tab goes back to the list.

## Users without a profile

| ID | Rule |
|---|---|
| USR-21 | A user may have **no permission profile**. That equals `negado` on every screen: the person can sign in, but the menu is empty and the home screen shows *"Você ainda não tem acesso a nenhuma tela. Fale com o responsável pelo sistema."* This is useful to register someone before deciding what they may do. |
| USR-22 | So that nobody forgets to choose a profile, saving a user without one asks for confirmation: **Salvar sem nenhum perfil?** *{Nome de exibição} vai conseguir entrar no sistema, mas não vai ver nenhuma tela até receber um perfil.* The options are **"Salvar sem perfil"** and **"Escolher um perfil"**, which goes back to the form. The list shows "Nenhum perfil" in the Perfis column. |

## The Admin system user

| ID | Rule |
|---|---|
| USR-23 | The **Admin** user always exists and cannot be changed, deactivated or deleted. It is stored in the database with a fixed id and marked `isSystem: true`, which makes the interface show it read-only with a notice explaining why (decision 16). |
| USR-24 | The Admin always has the Gerenciador profile and cannot lose it. Its e-mail comes from the server configuration; its password is the fixed one of the demo account (AUTH-13). |
| USR-28 | Changing or deactivating the Admin is refused with the message *"O usuário Admin é do sistema e não pode ser alterado nem desativado."* |
| USR-32 | *Retired: the `activatedAt` field left the record together with the `pending` status. It said the Admin was created with `activatedAt` empty.* |
| USR-33 | The Admin's e-mail is read from the configuration only when the Admin is first created; changing the configuration later does not change the stored record. |
| USR-34 | *Retired: the Admin has no mandatory password change (AUTH-15), and the `activatedAt` field left the record. It filled the Admin's `activatedAt` when it replaced its initial password.* |

| Field | Value |
|---|---|
| `id` | `00000000-0000-7000-8000-000000000001` |
| `login` | `admin` |
| `displayName` | Admin |
| `fullName` | Administrador do sistema |
| `status` | `active` |
| `profileIds` | The Gerenciador profile id, `00000000-0000-7000-8000-000000000002` |

Whether the Admin may have personal data (phone, signature) is an [open question](../open-questions.md); until then, it is a technical account.

## Signature

| ID | Rule |
|---|---|
| USR-25 | The signature is drawn on a 1200 × 400 pixel canvas, with the mouse or a finger, or uploaded as a PNG, JPG or WebP image of up to 5 MB. An uploaded image is resized to fit the canvas, keeping its proportions. |

The prototype stores the image inside the record as a *data URL* (PNG with a transparent background, or JPEG with a white background when larger than 180,000 characters). Separate object storage was evaluated and left out ("O que ficou de fora" in the [decisions document](../../decisoes-de-arquitetura.md)). **The signature is out of the first back-end slice**, and where it is stored is an [open question](../open-questions.md) (OQ-01).

## Operations

Minimum levels follow [permission profiles](permission-profiles.md#what-each-level-allows).

| Front-end method | Route | Minimum level | Notes |
|---|---|---|---|
| `listUsers({ page, pageSize, search, status })` | `GET /api/v1/users` | Reader | Paged, see below |
| `getUser(id)` | `GET /api/v1/users/{id}` | Reader | |
| `suggestLogin(fullName)` | `POST /api/v1/users/login-suggestion` | Editor | Full name in the body, never in the URL (personal data) |
| `createUser(data)` | `POST /api/v1/users` | Editor | `data` includes `temporaryPassword` (USR-35). Returns the created user |
| `updateUser(id, data, version)` | `PUT /api/v1/users/{id}` | Editor | Version in `If-Match` |
| `resetUserPassword(id, temporaryPassword)` | `POST /api/v1/users/{id}/reset-password` | Manager | AUTH-29. Answers 204; the password is not part of the record, so no version is sent |
| `deactivateUser(id, version)` | `POST /api/v1/users/{id}/deactivate` | Manager | |
| `reactivateUser(id, version)` | `POST /api/v1/users/{id}/reactivate` | Manager | |

**Listing.** `status` accepts `active` (the default), `inactive` or `all`. `search` looks in the display name, full name, login and CPF digits, ignoring accents and case. The response is `{ items, page, pageSize, totalCount }`, and each item has `profileNames` for the Perfis column. The prototype shows 10 users per page.

## Errors

| Status | `code` | When |
|---|---|---|
| 400 | `validation_failed` | Any rule in [validation on save](#validation-on-save) |
| 403 | `forbidden` | Operation above the person's level |
| 404 | `not_found` | Unknown user id |
| 409 | `concurrency_conflict` | CNV-13; `details.updatedByName` says who changed it |
| 409 | `system_record` | Changing or deactivating the Admin, or resetting its password (USR-23, USR-28, AUTH-15) |
| 409 | `self_deactivation` | USR-19, USR-27 |
| 409 | `not_inactive` | Reactivating a user who is not deactivated (USR-18, USR-29) |
