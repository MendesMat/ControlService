# Workflow: git and pull requests

Every change reaches `main` through a pull request. `main` is protected by the ruleset **Protect main**: pull request required, CI checks *Build and test* and *Build API image* must pass on an up-to-date branch, review threads resolved, linear history, squash merge only, no force push, no deletion, no bypass.

**Agents open pull requests; the owner merges them.** Stop after the pull request is open and CI is green. Merge only when the owner explicitly asks for a specific pull request ("pode juntar o PR #12").

## 1. Prepare

Check the identity, the branch and the working tree:

```bash
git config user.email
```

It must print `104966152+MendesMat@users.noreply.github.com`. If it does not, stop and tell the owner; do not commit.

Start from an updated `main`:

```bash
git switch main
git pull --prune
git status --short
```

If `git status` shows changes you did not make, stop and ask the owner what to do with them. Never discard or stash someone else's work silently.

**Always branch from an up-to-date `main`, never from another open branch.** Squash merges rewrite the base branch's commits, and fixing a stacked branch afterwards would need a force push, which is blocked. If your work depends on an open pull request, wait until the owner merges it.

## 2. Create a branch

```bash
git switch -c feat/cpf-value-object
```

| Prefix | For |
|---|---|
| `feat/` | New behavior |
| `fix/` | Bug fix |
| `refactor/` | Code change without behavior change |
| `test/` | Tests only |
| `docs/` | Documentation only |
| `ci/` | Workflows and pipelines |
| `chore/` | Build, tooling, dependencies |

Use short kebab-case names in English that describe the change.

## 3. Commit

- [Conventional Commits](https://www.conventionalcommits.org/) in English: `type(scope): summary`, imperative, lowercase, no period, at most 72 characters. Scopes are feature names: `users`, `auth`, `permission-profiles`, `access`, `api`, `adr`, `docker`, `ci`.
- One logical step per commit. The body explains **why**, when it is not obvious.
- Do not add `Co-authored-by` or "generated by" lines: the owner decided that commits appear only under their name.
- Never commit build output, secrets, `.vs/` or files outside the change.

```
feat(users): validate CPF check digits

CPF is informational (CNV-06), so only the check digits and the
all-equal-digits rule are enforced (USR-08); uniqueness is not required.
```

## 4. Verify locally

From `backend/ControlService`, both must succeed with zero warnings:

```bash
dotnet build ControlService.slnx
```

```bash
dotnet test --solution ControlService.slnx
```

## 5. Push and open the pull request

```bash
git push -u origin feat/cpf-value-object
```

Write the pull request body to a file, following `.github/pull_request_template.md` (What, Why, How to test, Checklist). Then:

```bash
gh pr create --base main --title "feat(users): validate CPF check digits" --body-file pr-body.md
```

- The title follows Conventional Commits: it becomes the commit message on `main` after the squash merge.
- When the work comes from an issue, the body contains `Closes #<number>`, so GitHub closes the issue when the owner merges. One pull request per issue; a large issue may be delivered in several pull requests, and only the last one closes it (the others say `Part of #<number>`).
- Keep pull requests small and focused; split unrelated changes.
- Use `--draft` while the work is incomplete, and `gh pr ready` when it is done.
- Do not enable auto-merge.

## 6. Wait for CI

```bash
gh pr checks --watch
```

If a check fails, read the log (`gh run view <run-id> --log-failed`), fix the cause on the same branch, commit and push again. If `main` moved and the branch is behind, update it:

```bash
gh pr update-branch
```

## 7. Hand over to the owner

When CI is green, tell the owner in Portuguese: the pull request link, what changed, how you verified it, and anything they should look at closely. Then stop.

## 8. After the owner merges

Confirm the pull request is merged:

```bash
gh pr view <number> --json state
```

Only if it prints `"state":"MERGED"`, update `main` and delete the local branch:

```bash
git switch main
git pull --prune
git branch -D feat/cpf-value-object
```

`-D` is needed because a squash merge creates a new commit on `main`, so git does not recognize the branch commits as merged. The remote branch is deleted by GitHub automatically. Never delete a branch whose pull request is still open or was closed without merging, unless the owner asks.

## Never

- Push to `main`, force push to a shared branch, or rewrite history that is already on GitHub.
- Merge a pull request without the owner's explicit request, or with failing checks.
- Change the ruleset, repository settings or CI requirements to get a change through.
- Use `--no-verify`, or delete or skip tests to make CI pass.
