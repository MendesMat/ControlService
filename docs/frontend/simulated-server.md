# Simulated server

While the back-end is being built, the [front-end prototype](README.md) carries a layer called the **simulated server** (`createSimulatedServer`, in the "Simulated server" section of the script). It plays the role of the back-end:

- it offers the operations documented in [product/features](../product/features/);
- it applies the rules of [product](../product/): validation, uniqueness, version, authorship, deactivation, access by level, single-use links and lockout;
- it returns errors in the same format as the back-end ([API conventions](../api/conventions.md#errors)).

Screens never access data directly: they only call the methods of the `api` object. **To connect the real back-end, replace `createSimulatedServer` with a client that makes the HTTP calls and offers the same methods, with the same responses and errors.** No screen needs to change.

## Where the simulation stores data

It uses the Claude artifact database when the page is open inside Claude. If that does not answer within 4 seconds, or fails to load, it uses the browser's `localStorage` (keys `control-service:dados:*`). It keeps five collections:

| Collection | Content |
|---|---|
| `users` | Users, as in [users](../product/features/users.md#data-model) |
| `profiles` | Permission profiles |
| `credentials` | Hashed password and lockout counter of each user |
| `tokens` | Activation and reset links, stored only hashed |
| `emails` | "Sent" e-mails, shown in **E-mails de teste** |

## Test inbox

The simulation does not send real e-mails. Activation and reset e-mails are stored and shown by the **E-mails de teste** button (envelope icon in the top bar and on the sign-in screen), newest first. Each e-mail has the link button, which opens the matching screen. The `listEmails()` method exists only in the simulation; in the real back-end, Mailpit plays this role (ADR-0030). In the simulation, sending never fails.

## Session

The simulated session is stored in the browser (`control-service:sessao`) and lasts **8 hours from the last action**. On every operation, the simulated server checks that the session is still valid and the account still active. The real back-end keeps the same behavior with tokens (AUTH-17, AUTH-18).

## Demo access

On first access, the login is `admin` with the initial password `admin123`, and the system asks for a new password. The sign-in screen shows this instruction. How reviewers will sign in to the public demo of the real back-end is an [open question](../product/open-questions.md).

## Differences from the real back-end

The simulation already follows the decided model. The HTTP client that replaces it must handle these differences:

| Topic | Real back-end | Simulated server |
|---|---|---|
| Identifiers | UUID v7 generated by the server; fixed GUIDs for the system records (ADR-0012). The front-end stops generating ids and reads them from the creation response | UUID v4 generated by the simulation. The system records use `sistema-admin` and `sistema-gerenciador` |
| System records | Stored in the database (ADR-0022) | Defined in the simulation's code and added to queries |
| Signature | Still open: ADR-0018 proposes separate object storage; out of the first back-end slice | Stored inside the record as a *data URL* |
| Passwords | Hashed by ASP.NET Core Identity (ADR-0019) | SHA-256 with a random salt per user; for the demo only |
| Session | Access token in memory and refresh cookie (AUTH-17) | Session record in `localStorage` |
| Errors | Problem Details, converted to `ApiError` by the client (API-12) | `ApiError` directly |

Records created before these decisions are converted automatically when the prototype opens: CPF, phone and CEP become digits only, the login is suggested from the name, the status becomes pending, and authorship and version are filled in. Since those records had no e-mail, one must be registered before resending access.
